# PART II: Authentication Methods

## Chapter 5: Password Authentication

### Definition
Password authentication is a knowledge-based authentication mechanism where a user proves their identity by providing a pre-shared secret (a password) that only they and the server should know.

### Working and Internal Architecture
1. **Registration:** User submits a plaintext password over TLS. The server generates a random string called a `salt`. The server concatenates the password and the salt and hashes them using a slow algorithm (e.g., bcrypt, Argon2). The resulting hash and salt are stored in the database. The plaintext password is immediately discarded from memory.
2. **Authentication:** User submits their plaintext password. The server retrieves the salt and the stored hash for that user. The server runs the same slow algorithm on the submitted password combined with the retrieved salt.
3. **Validation:** The server performs a constant-time comparison of the resulting hash against the stored hash.

### Advantages
- **Ubiquity:** Universally understood by all users.
- **No hardware dependency:** Users do not need a smartphone or physical token.
- **Revocability:** Easy to reset if compromised.

### Disadvantages
- **Vulnerability:** Highly susceptible to brute-force, dictionary, and credential stuffing attacks.
- **Human Factor:** Users reuse passwords and choose weak ones.
- **Phishing:** Passwords can easily be intercepted by fake websites.
- **Storage Risk:** If the database is breached, weak hashes can be cracked.

### Use Cases
- Legacy systems.
- Low-security applications (e.g., forums).
- As a fallback mechanism when primary Passwordless factors fail.

### Implementation and Production Architecture
In production, passwords should never be used as the *sole* factor for sensitive data. 

**Production Architecture Components:**
- **TLS/HTTPS:** To prevent plaintext interception in transit.
- **Rate Limiter (e.g., Redis):** To prevent brute-force attacks by limiting attempts per IP and per username.
- **KDF (Key Derivation Function):** bcrypt (work factor >= 12) or Argon2id.
- **zxcvbn:** A library used on the frontend and backend to estimate password crack time and enforce complexity without relying on outdated Regex rules (like "must have one special character").

### Interview Questions
- **Q:** Why do we add a "salt" to a password before hashing?
  - **A:** A salt ensures that two users with the same password do not have the same hash in the database. It prevents attackers from using pre-computed "Rainbow Tables" to instantly crack large batches of passwords.
- **Q:** Why is a slow hash like bcrypt better than a fast hash like SHA-256 for passwords?
  - **A:** Attackers use GPUs to compute billions of SHA-256 hashes per second. Bcrypt is intentionally slow and CPU-intensive, drastically slowing down an attacker's ability to brute-force a stolen database.

## Chapter 6: PIN Authentication

### Definition
A Personal Identification Number (PIN) is a numeric password, typically 4 to 6 digits, used for quick, local authentication.

### Working and Internal Architecture
Unlike passwords, PINs are usually tied to a specific physical device or a physical token (like a smart card). 
- **Local PIN:** Unlocks a Secure Enclave or Trusted Execution Environment (TEE) on a smartphone. The PIN never leaves the device.
- **Server PIN:** Used in banking systems (ATMs). The PIN is encrypted at the ATM hardware level using a master key and sent to a Hardware Security Module (HSM) in the bank's data center for verification.

### Advantages
- Very fast user experience.
- Easy to input on mobile or limited keypads.

### Disadvantages
- Low entropy (a 4-digit PIN only has 10,000 combinations).
- Relies heavily on strict rate limiting (lockout after 3-5 failed attempts) to prevent brute force.

### Use Cases
- Mobile app quick unlocks (banking apps).
- ATM withdrawals.
- SIM card unlocking.

### Interview Questions
- **Q:** If a 4-digit PIN is so mathematically weak, why do banks use it for ATMs?
  - **A:** Because a PIN is a *two-factor* system. You must possess the physical ATM card (Factor 1: Possession) and know the PIN (Factor 2: Knowledge). Furthermore, the ATM limits you to 3 attempts before swallowing the card, rendering a brute-force attack impossible.

## Chapter 7: OTP Authentication (One-Time Password)

### Definition
An OTP is an automatically generated numeric or alphanumeric string that authenticates a user for a single transaction or login session. 

### Working and Internal Architecture
There are two main types of OTPs:
1. **Time-based OTP (TOTP):** Generated by apps like Google Authenticator. Both the server and the app share a secret seed (scanned via QR code). The current Unix timestamp (divided by 30 seconds) is hashed with the seed using HMAC-SHA1 to generate a 6-digit code.
2. **Delivery-based OTP (SMS/Email):** The server generates a random 6-digit number, stores it in a cache (like Redis) with a short TTL (Time To Live, e.g., 5 minutes), and sends it to the user via SMS or email.

### Advantages
- Mitigates password reuse and credential stuffing.
- Short lifespan makes replay attacks difficult.

### Disadvantages
- **SMS OTPs are vulnerable:** They can be intercepted via SIM swapping attacks, SS7 network vulnerabilities, or compromised devices.
- **TOTP UX:** Requires the user to install a separate authenticator app.
- No defense against real-time phishing proxies (like Evilginx).

### Use Cases
- Standard 2FA for web applications.
- Password reset flows.
- Approving high-risk transactions.

### Implementation and Production Architecture
**Production Example (TOTP Verification flow):**
1. User enters Email + Password.
2. Server validates password and returns `{ status: "MFA_REQUIRED", temp_token: "xyz" }`.
3. User opens Google Authenticator and enters the 6-digit OTP.
4. App sends `{ temp_token: "xyz", otp: "123456" }`.
5. Server uses `speakeasy` or `otplib` to compute the expected TOTP using the user's stored secret and current time. If it matches, the final JWT is issued.

### Interview Questions
- **Q:** Explain how Google Authenticator works offline.
  - **A:** It uses TOTP (Time-Based One-Time Password). The app and the server share a secret key established during setup. The app generates the code using only the secret key and the device's current clock time. No internet connection is needed because the server runs the exact same mathematical function using the same secret and time.

## Chapter 8: Magic Link Authentication

### Definition
A passwordless authentication flow where a user inputs their email, and the server emails them a uniquely generated link containing a secure, short-lived token. Clicking the link authenticates the user.

### Working and Internal Architecture
1. Client requests login for `user@domain.com`.
2. Server generates a high-entropy token (e.g., a UUID or signed JWT).
3. Server saves the token in a database/Redis linked to the `user_id`, setting an expiration (e.g., 15 minutes).
4. Server emails the link: `https://app.com/verify?token=XYZ`.
5. User clicks the link. The browser makes a GET request to `/verify`.
6. Server validates the token, marks it as used (to prevent replay), and issues a session cookie.

### Advantages
- Removes the need for users to remember passwords.
- Defeats brute-force password attacks.
- High conversion rate for onboarding.

### Disadvantages
- Highly dependent on the security of the user's email account.
- Terrible UX on mobile if the link opens in an embedded webview instead of the native app.
- Email delivery issues (spam filters, corporate link scanners clicking the link prematurely).

### Use Cases
- B2B SaaS applications (e.g., Slack, Notion).
- Newsletters (e.g., Substack).

### Production Architecture
To prevent corporate email scanners (which visit every link in an email to check for malware) from accidentally consuming the one-time token and logging the user in on a headless server:
- **Best Practice:** The Magic Link should *not* log the user in immediately via a GET request. Instead, the link should open a webpage that requires the user to explicitly click a button ("Confirm Login") which sends a POST request.

## Chapter 9: WebAuthn and Passkeys

### Definition
WebAuthn (Web Authentication) is a W3C standard for secure, passwordless authentication using public-key cryptography. A **Passkey** is the consumer-friendly name for a discoverable WebAuthn credential that can be synced across devices via cloud ecosystems (like iCloud Keychain or Google Password Manager).

### Working and Internal Architecture
WebAuthn removes shared secrets entirely.
1. **Registration (Creating the Passkey):**
   - Server sends a challenge (random string) to the browser.
   - Browser prompts the OS authenticator (FaceID, TouchID, Windows Hello).
   - The OS generates a private/public key pair securely inside its TPM/Secure Enclave.
   - The private key *never* leaves the device.
   - The public key is sent to the server and stored in the database.
2. **Authentication (Using the Passkey):**
   - Server sends a challenge.
   - OS prompts the user for biometrics to unlock the private key.
   - The private key signs the challenge, creating a digital signature.
   - The signature is sent to the server.
   - The server uses the stored public key to verify the signature.

### Advantages
- **Phishing-Resistant:** The browser binds the cryptographic signature to the origin domain (e.g., `github.com`). If a user is on `githuub.com`, the browser will refuse to sign the challenge with the `github.com` key.
- No passwords to steal.
- No shared secrets on the server (a database breach only yields useless public keys).

### Disadvantages
- Complex to implement on the backend (requires parsing CBOR data structures).
- UX can still be confusing for non-technical users.
- Cross-ecosystem syncing (Apple to Windows) is improving but traditionally complex.

### Use Cases
- Consumer applications replacing passwords (e.g., GitHub, Google, Apple, Amazon).
- High-security enterprise systems.

### Implementation
**Relying Party (RP):** Your web server.
**Authenticator:** The user's device (phone, YubiKey).
Implementations often use libraries like `@simplewebauthn/server` for Node.js to handle the complex attestation and assertion verifications.

### Interview Questions
- **Q:** How does WebAuthn defeat phishing?
  - **A:** The WebAuthn API requires the browser to include the `Relying Party ID` (the domain name) in the cryptographic signature. If an attacker lures a user to `fake-bank.com`, the browser will look for a passkey registered to `fake-bank.com` and find nothing. The attacker cannot trick the browser into providing the signature for `real-bank.com`.

## Chapter 10: OAuth 2.0 & OpenID Connect (Single Sign-On / Federated Identity)

*(Note: OAuth and OIDC are massive topics and will be covered in extreme depth in Parts VI and VII. This is a high-level overview of their use as Authentication Methods).*

### Definition
**Single Sign-On (SSO):** Allowing a user to log in once to a central authority and access multiple independent applications without logging in again.
**Federated Identity:** A form of SSO where trust is established across organizational boundaries (e.g., logging into Spotify using a Facebook account).

### Working and Internal Architecture
Instead of storing passwords, the application delegates identity verification to a trusted Identity Provider (IdP) like Google, Microsoft, or an enterprise Active Directory.
1. User clicks "Login with Google".
2. App redirects user to `accounts.google.com`.
3. User authenticates with Google.
4. Google redirects back to the App with an Authorization Code.
5. App backend exchanges the code with Google for an `ID Token` (OIDC) and an `Access Token` (OAuth).
6. App reads the ID Token to verify the user's identity.

### Advantages
- Users don't have to create new passwords.
- Centralized security policies (if a company enforces MFA on Google Workspace, all connected internal apps inherit that MFA).
- Immediate user provisioning.

### Disadvantages
- Single point of failure (if the IdP goes down, nobody can log in).
- Vendor lock-in.

### Enterprise Authentication (SAML vs OIDC)
In the enterprise space, Federated Identity is often handled by **SAML 2.0 (Security Assertion Markup Language)** or **OIDC (OpenID Connect)**.
- **SAML:** Older, XML-based. Highly robust, used by older enterprise software. Relies on heavy XML parsing and XML signatures.
- **OIDC:** Modern, JSON-based (built on top of OAuth 2.0). Lightweight, standard for modern web and mobile apps. Uses JWTs.

### Production Architecture
An enterprise B2B SaaS application (like Salesforce or Jira) must support SP-Initiated (Service Provider) and IdP-Initiated flows. It requires dynamic routing to determine which IdP to forward the user to based on their email domain (e.g., `user@companyA.com` goes to Okta, `user@companyB.com` goes to Entra ID).

### Interview Questions
- **Q:** What is the difference between OAuth 2.0 and OpenID Connect?
  - **A:** OAuth 2.0 is an *authorization* framework designed to delegate access (e.g., "Let App X read my Contacts on Google"). It does not provide identity. OpenID Connect is an *authentication* layer built on top of OAuth 2.0 that provides identity via a JWT called an ID Token. Using plain OAuth 2.0 for authentication is a security anti-pattern.
